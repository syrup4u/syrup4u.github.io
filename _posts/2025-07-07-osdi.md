## Database Systems

**Tigon: A Distributed Database for a CXL Pod**

Network issues of scaling out of database:

- Message exchange (two-phase commit)
- RDMA (remote share memory)

Avoid using network by using only memory.

CXL (Compute Express Link): connect to the same memory by directly connection (not switch).

Approach:

1. PCIe for message exchange. Still two-phase and numerous messages.
2. Shared data in CXL memory. High latency and low bandwidth compared to DRAM.

Store locally initially. And move data to CXL memory depending on the request.

Frequent data movement (limited hardware cache):

- Software cache coherence to cache key metadata (latches / locks across hosts). So that more data can be stored in CXL memory even without hardware coherence (so no need to exchange more often).
- Only copy modified tuples.

Avoids 2PC by adopting value logging. Reconstruct internal state upon recovery.

- Tuple modification: ok in CXL memory.
- Indexes modification: can be reconstructed during recovery (no need to log index modification).
- Only be logged by the host who execute the tx.

**Mako: Speculative Distributed Transactions with Geo-Replication**

RDMA is not working when it comes to geo-replication.

Decouple replication from 2PC.

But rollback? too many unnecessary rollback of transactions.

2PC failed:

1. one failed, one ok: delay decision until the replication is ok.
2. dependency? Epoch to batch transaction. Abort or submit all transactions in a epoch.
3. Excessive rollbacks (Some unrelated txns)? Vector clock to track dependencies.

**Achieving Low-Latency Graph-Based Vector Search via Aligning Best-First Search Algorithm with SSD**

Dependency => latency. One I/O for each candidate.

So pipeline search. Read until full then compute.

- Parallel reads: low latency
- Speculative reads: low throughput

I.e., narrow pipeline => high throughput (less computation); wide pipeline => low latency (less I/O waiting by overlapped reading) => accumulation of read-but-unexplored.

Two techniques:

1. Dynamic pipeline width (growing unexplored top-k neighbors). Approach phase, less target vectors (in the critical path) in the candidate pools, so lower width. Converge phase, more target vectors in the vector, so increase the width.
2. upper bound for the number of unexplored neighbors (avoid accumulation by sacrificing a little latency). Reduce missing rate by delaying some I/O fetches, only after one computation finished.

**Skybridge: Bounded Staleness for Distributed Caches**

Write results become visiable eventually (Consistency). But how long? Bounded staleness.

Because cache misses result in staleness.

Fine grained, which shard or cache is stale.

Skybridge (vs. DB relication):

- only metadata.
- Allow data loss. (leads to indetermined)
- Out of order (network issues).

achieve 2-second cache consistency (99%).

## Distributed Systems and Data Centers II

**Low End-to-End Latency atop a Speculative Shared Log with Fix-Ante Ordering**

Problem: high APP e2e latency

Key idea: overlap ordering => perfect speculation for execution order

shared log ordering is expensive => speculative orders and confirm later

but predict is hard because of arbitrary report of records of each shard

So fix the number:

- more: then delay
- lack: then add no-op.

Whole shard failure is rare so less failed speculation. View-change protocol to deal with this case.

**Understanding Stragglers in Large Model Training Using What-if Analysis**

gradient updating => some stragglers are slow

layer: P2P communication (PP)
gradient: Sync (TP)
batch: partition (CP/DP)

Traces to do the statistics of staggler rates. Simulation to find the root cause.

Root cause:

1. worker (hardware) problems. Not a common case, but once it happens, it's super slow.
2. Imbalance or layer loss is the main root cause.

In production analysis to find out the stagglers.

**Fork in the Road: Reflections and Optimizations for Cold Start Latency in Production Serverless Systems**

High tail latency under concurrent case: Fork-based cold start.

InitCode (238.73 ms, slow) vs. Execution (36.8 ms)

1. Shorten control path (sacrify modularity) to speed up.
2. resource contention. Solved by pooling and sharing.
3. User code initialization. Solved by tree-structured seeds with multi-level forking.

**Kamino: Efficient VM Allocation at Scale with Latency-Driven Cache-Aware Scheduling**

VM request throughput and latency, this one focus on allocator latency.

tail latency under bursts.

memory efficiency is the root cause (cache misses).

load balancing is not friendly to cache locality.

cache-ware for expensive requests instead of cheap requests.

estimate the time of a request (under cache and load balancing)

So the key is how to reconcile cache with load balancing

**ZEN: Empowering Distributed Training with Sparsity-driven Data Synchronization**

gradient can be dense or sparse (value zero).

very similar to my previous research on blockchain, many zeros can be shrinked during synchronization.

balanced parallelism: Skewed distribution of non-zero gradients => leads to unbalanced sync and aggregation.

hash memory management (to solve the sync imbalance). Hash the indice of the non-zero gradients.

## Kernel and Operating Systems II

**XSched: Preemptive Scheduling for Diverse XPUs**

1. Lack of preemption support.
2. Hardware schedule is not flexible.
3. Existing solutions are not general.

Abstract to command sequence. And suspend + resume.

Common assumption + adative.

Multiple levels to support different advanced XPU features.

**OS Rendering Service Made Parallel with Out-of-Order Execution and In-Order Commit**

1. CPU is the bottleneck of 2D rendering performance.
2. multi-core is not fully utilized (skewness).

want fine-grained parallelization (compared to existing STOA solutions).

- In-order preparation (main thread): complete depedencies.
- Out-of-order execution: independent tasks can be executed statelessly.
- In-order commit: those overlap (self-contained) tasks are committed in order.

**EMT: An OS Framework for New Memory Translation Architectures**

Miss evaluation of new memory translation (page) techniques on OS. (due to compatibility or heterogeneous)

Virt. => Phys. can be represented by translation object, and that object can be stored in database.

Customized function to support some unique for different MMUs.

Thus, functional kernel and performant kernel.

Overall, it introduces a layer to provide compatibility (support) for different translation architectures without the needing to heavily modify the memory management code.

**Tiered Memory Management Beyond Hotness**

Hotness (frequency) is not enough, sometimes even slower than the cold ones.

Reduce unnecessary page migration (of hotness). Enable / disable page promotion based on "amortized offcore latency".

amortized offcore latency (AOL), a novel metric that precisely captures the true performance impact of memory accesses by accounting for memory access latency and memory-level parallelism (MLP).
